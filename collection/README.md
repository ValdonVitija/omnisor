# Collection configuration

Runtime configuration for the standalone desktop. These files are bundled into
`omnisor-collection` at build time, so an installed application does not depend on
its working directory or a source checkout. Never put device credentials here.

```text
collection/
  components.yaml                 # tested binary versions and asset locations
  catalog.yaml                    # explicit list of available profiles
  collector/base.yaml             # shared OTLP pipeline / resource limits
  exporters/snmp/v0.29.0/
    system.yaml                   # upstream generated MIB modules
    if_mib.yaml
    cisco_device.yaml
    cisco_ios_legacy.yaml          # generated legacy CPU / processor RAM scalars
    generator/cisco-iosvl2/        # generation input and locked MIB provenance
    LICENSE, NOTICE, PROVENANCE.md
  profiles/
    common/if-mib/profile.yaml     # shared system + interface normalization
    vendors/cisco/ios/
      generic/profile.yaml        # IOS/IOS-XE CPU + memory, inherits IF-MIB
      models/iosvl2/profile.yaml  # validated legacy CPU / processor RAM mapping
    generic/prometheus/profile.yaml
    synthetic/profile.yaml
```

An adapter describes how collection happens. A device profile describes the
exporter schema and entity identities. A model/OS version may inherit a broader
profile and override only changed mappings or module requirements. Avoid a full
copy of the Collector/exporter YAML for every model or device. The current
catalog resolves collection from a selected device family or saved device record;
engineers do not select a protocol or exporter. It does not automatically discover
a device's model/OS or infer exact compatibility from a vendor name.

`extends` resolves parents first and applies child mappings last. SNMP modules
merge without duplicates. Connection policy is inherited unless overridden;
conflicting parent policies require an explicit child policy. Missing parents/assets, duplicate IDs, inheritance
cycles, and excessive depth are rejected. Add a new profile's path to
`catalog.yaml`; the build embeds YAML assets recursively. More adapters can use
the same normalized observations and history without changing the dashboard.

For a future validated model override:

```yaml
id: vendor-os-model-version
revision: '1'
title: A validated model and software release
extends: [cisco-ios-snmp]
vendor: Cisco
os: IOS
support: Record the exact image/model/version and validation evidence here.
adapters: [snmp]
# snmp_modules: [another_generated_module]
# mappings: {only_the_metrics_that_changed: ...}
```

Keep module definitions generated by the upstream MIB generator. Their provenance
is in [the versioned directory](exporters/snmp/v0.29.0/PROVENANCE.md). Do not replace
MIB walking with command-output parsing. The SNMP serializer preserves native
YAML integer enum keys; converting module trees through JSON breaks the strict
exporter decoder. The planner builds the Collector config structurally and
escapes literal dollar signs before OTel environment expansion.

## Device access resolution

The headless planner in `omnisor-collection::access` owns source selection.
A profile with a `device` descriptor is available as a friendly device family.
Its internal `connection` policy determines source, port, cadence, and required
credentials. Model/version profiles can inherit a family and override only what
changes. For example, the Cisco family currently defines:

```yaml
device:
  label: Cisco IOS / IOS-XE
connection:
  kind: snmp_v3
  port: 161
  interval_seconds: 10
```

Policies currently support `snmp_v3` (SHA/AES authPriv), `snmp_community`, and
`prometheus` (scheme, port, path, bearer requirement). The GUI asks only for the
corresponding credentials and the device address. Blank credentials fail validation;
they never switch protocols. Do not assume that vendor/model determines a site's
configured access: saved device/site routing can point to an existing exporter.
Further capability negotiation and OS discovery remain separate future work.

Optional saved device records use this non-secret JSON schema:

```json
{
  "schema_version": 1,
  "devices": [{
    "id": "gns3-iosvl2",
    "name": "lab-cisco-iosvl2",
    "address": "127.0.0.1:1161",
    "profile_id": "cisco-iosvl2",
    "connection": {
      "kind": "snmp_community",
      "port": 161,
      "interval_seconds": 10
    },
    "credentials_file": "/absolute/path/to/private-lab-auth.json"
  }]
}
```

`connection` is an optional site override of the model's default access policy;
metric mappings still come from the device profile. It handles deployment-specific
authentication without asking the engineer to choose a protocol. `credentials_file`
is an optional **absolute file reference**, read only after Connect. The referenced
JSON supports `username`, `password`, `privacy_password`, and `access_key` (or
`community` for a provisioned SNMPv2c lab). It must be a regular file of at most
16 KiB, with private permissions (0600 on Unix). Secret contents never enter saved
device metadata or parse-error diagnostics. A missing/invalid file fails connection
rather than silently changing access method. Source files stay in place; session
copies are removed on Stop. This is an initial local credential provider, not an
OS keychain integration.

Alternatively, `gateway: {metrics_url: "https://exporter.example/metrics",
bearer_required: true}` selects an existing exporter and requests an access token.
A gateway cannot be combined with a direct `connection` override. Upstream
credentials then belong in that external exporter. Userinfo and credential URL
query keys are rejected. Changing to a new device cannot retain a saved route.

Records load once at startup from `OMNISOR_DEVICES_FILE`, or the first
`collection-tools/devices.json` beside the executable or its parent. The file is
bounded to 64 KiB and validates unique IDs, known device policies and endpoints.
No component starts while reading it. Credentials are not saved. `tests/lab/gns3/telemetry.py`
registers the local lab record after configuring its UDP transport. The desktop
starts both native exporter and Collector when the engineer connects.

Executables resolve internally from developer environment overrides, PATH, or
companion component directories. Missing components report an installation error;
engineers do not choose binaries in the connection form. Platform packaging and
verified binary delivery remain release work.

## What a connection starts

1. Resolve the device record/family and access requirements into a typed collection
   plan; validate its target, credentials, profile, cadence and component paths.
2. Bind a session-authenticated OTLP/HTTP protobuf receiver on `127.0.0.1:0`.
3. Create a private temporary session directory (0700 on Unix), with config files
   restricted to 0600.
4. For SNMP, compose only the selected upstream modules and session auth, start
   `snmp_exporter` on an ephemeral loopback port, and check readiness.
5. Generate a Collector scrape job using trusted device labels, mapped-metric
   filtering, a sample/label budget, and the local OTLP destination. Run the
   selected `otelcol-contrib` binary. Prometheus endpoints use this same pipeline
   without starting an SNMP exporter.
6. Normalize OTLP into shared observations and update bounded history. The GPUI
   thread reads immutable snapshots; it never scrapes or waits for subprocesses.
7. Stop in reverse order, reap children, close the listener, then remove session
   credentials/configuration. Unix children use separate process groups.

The Collector owns Prometheus parsing, scraping, retry/batching, and OTLP export.
The Rust application owns configuration, process lifetime, local receiving,
normalization, history, calculations, and presentation. There is no Prometheus
server or cloud dependency. The synthetic adapter hosts an explicitly simulated
exporter locally and runs through the real Collector/receiver, not a UI timer.

SNMPv3 currently uses authPriv with SHA authentication and AES privacy. SNMPv2c
supports an explicit read-only community. Community/password fields are masked
in the form. SNMP secrets exist in the private temporary exporter file for the
session; Collector/source bearer tokens are passed through child environment
variables. Component logs are bounded and redacted. No credentials are embedded
in bundled assets or saved device metadata. The lab uses an ignored private source
file referenced by its device record; its session copies are cleaned up normally.
Crash recovery and OS keychain integration remain future work.

## Profiles and coverage

- `generic-if-mib`: system description/name/object ID, SNMP agent uptime,
  interface admin/oper state, 64-bit receive/transmit octets, errors, and discards.
  Interface index is the series identity; `ifName` remains a display attribute.
- `cisco-ios-snmp`: inherits that coverage and adds one-minute CPU and memory
  pool used/free. A pool's type index is its identity, not its display name.
- `cisco-iosvl2`: inherits system/interfaces from IF-MIB and uses the generated
  `cisco_ios_legacy` module: `avgBusy1` (one-minute exponentially-decayed CPU average),
  `processorRam` (CPU RAM bytes), and `freeMem` (free bytes). CPU normalizes percent
  to ratio. Processor used RAM is derived from total − free, then utilization from
  used / (used + free), joining the same entity and exact scrape timestamp. These
  legacy OIDs are validated on the 20190423 image; its newer Cisco CPU/memory MIB
  trees return noSuchObject. A site policy configures access independently.
- `native-prometheus`: a documented mapping contract, not universal exporter
  auto-discovery. It accepts `omnisor_cpu_utilization_ratio{cpu}`,
  `omnisor_memory_{used,free}_bytes{pool}`,
  `omnisor_interface_{admin,oper}_status{interface}`, and
  `omnisor_interface_{receive,transmit}_bytes_total{interface}`. States follow
  IF-MIB numeric enums. Add another profile to support a different endpoint schema. Exporter URL query parameters such as `target`, `module`, and named `auth` are preserved, including repeated values; credentials belong in the bearer field or exporter configuration.
- `synthetic`: reuses that contract for the local changing exporter.

The Cisco and IF-MIB profiles are experimental until validated against exact
hardware/software combinations. Unsupported metrics remain unavailable. Catalog-derived
vendor/model/type/OS are connection context, not verified discovery. Reported SNMP
hostname, description, object ID, and uptime appear separately; a description
string does not establish verified hardware identity.

## Statistics and limits

- History is in RAM: at most 4096 series, 450 points per history series, and
  15 minutes by timestamp. Raw counters and non-chart gauges retain two points.
- Series are ordered by observation time; duplicate/older deliveries do not
  rewind them. Unenrolled devices, invalid values, far-future and expired points
  are rejected. Capacity drops are counted and visible.
- CPU retains the source averaging window. Memory utilization joins used/free
  from the same entity and exact timestamp. A total/free pair can derive used bytes
  only when both are gauges in bytes, total > 0 and 0 ≤ free ≤ total. Profiles must
  map total/free to the same actual memory scope; chassis memory and an unrelated
  pool cannot be combined. Direct used/free measurements take precedence within a batch. The Collector assigns scrape timestamps
  consistently (`honor_timestamps: false`).
- Traffic is `8 * counter_delta / elapsed_seconds`. It needs two samples, a
  matching counter epoch, no decrease/reset, and a gap within 1.5 scrape intervals.
  Missing/reset intervals do not become zero traffic. Aggregates sum observed
  interface rates at matching timestamps and are cached outside rendering.
- Graphs show actual time, axis units, sample count, min, max, and arithmetic
  sample mean. This mean is not a time-weighted average or a percentile. CPU/memory
  select one identified series; traffic is labeled as observed interface totals.
- Current resource summaries require `up=1` and observations no older than three
  scrape intervals. Failed/stale/stopped collection cannot appear healthy.
  Historical graphs and last interface states remain visibly historical.
- The receiver accepts authenticated, uncompressed OTLP/HTTP protobuf, capped at
  1 MiB per request. Collector queues, batches, memory use, and scrape samples are
  bounded. There is no automatic restart loop in this first supervisor.

This is one active device session in the desktop, with reusable plans/session
handles. Persistent multi-device inventory, shared component pooling, binary
packaging/update delivery, gNMI adapters, and model discovery are subsequent slices.

## Validation

```sh
cargo test -p omnisor-collection -p omnisor-desktop -p omnisor-telemetry
OMNISOR_TEST_COLLECTOR=/path/to/otelcol-contrib \
OMNISOR_TEST_SNMP_EXPORTER=/path/to/snmp_exporter \
cargo test -p omnisor-collection --test pipeline -- --ignored --nocapture
```

The binary tests exercise successful real scraping/OTLP/rates and failed SNMP
targets, process reaping, listener closure, private file modes, and directory
cleanup. They do not establish Cisco image compatibility.

Configuration follows the pinned
[Collector Prometheus receiver](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/v0.140.0/receiver/prometheusreceiver/README.md),
[OTLP/HTTP exporter](https://github.com/open-telemetry/opentelemetry-collector/blob/v0.140.0/exporter/otlphttpexporter/README.md),
and [SNMP exporter](https://github.com/prometheus/snmp_exporter/tree/v0.29.0).
